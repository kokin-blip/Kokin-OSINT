Date: 2026-08-12 · Branch: `feat/phase0-foundations`

Reference-workflow steps 2 and 3: a URL becomes provenance and lineage. This is
the first increment where the earlier crates compose — the store, the key
hierarchy, the blob store and the replay harness all appear in one call path.

Landed in two halves. **6a** added the schema (committed separately, see
`464f998`); **6b** adds the pipeline that writes into it. They are reported
together because neither is meaningful alone: a schema with nothing writing to
it is untested, and a pipeline needs somewhere to write.

Still **no live transport**. Every test drives `ReplayHttp`.

## The three ideas

**The run row is opened before any work and closed after.** A crash mid-fetch
leaves a `running` row rather than no evidence that anything was attempted, and a
failed fetch is completed as `failed` with a stable `error_code` before the error
is returned. A pipeline that records only its successes cannot be audited, and
"nothing happened" and "something happened and failed" must not look identical.

**Identity lives on `source`, history lives on `capture`.** An existing
`canonical_locator` is reused rather than duplicated, so the same page fetched
twice is one source with two captures. That is what makes *when did this change?*
a question the case can answer at all. The canonical form comes from
`url_norm::normalise` — the same function that keys fixtures, so replay and
evidence identity cannot drift apart (increment 5b).

**A dedupe hit is trusted only when the row backing it exists.** See below; this
one came out of a bug.

Six new tests in `kokin-ingest`. What each is for:

- **a fetched url becomes provenance and lineage** — the whole trail in one
  assertion set: one row in each L0 table, both `derivation` edges walkable via
  the run, `capture_completeness = 'static_html_only'`, `from_fixture = 1`, the
  connector and job recorded, and the run closed as `succeeded`.
- **refetching a url adds a capture without duplicating the source** — one
  source, two captures, one blob.
- **a missing fixture leaves a failed run and no evidence** — the run says
  `net.no_fixture`; `source`, `capture` and `artifact` are all empty. A cache
  miss under replay is a failure, never a live call (A-018).
- **an unsuccessful response is not recorded as evidence** — a 404 body is not
  the page, and recording it as an artifact would let an error page be cited as
  evidence of what was at that URL.
- **an orphaned blob does not poison later ingests** — the bug below.
- **an ingest is recorded in the audit chain** — `evidence.ingested`, carrying
  `from_fixture`, with the chain still verifying afterwards.

## A bug the tests caught

`BlobStore::put` decides `AlreadyPresent` from the presence of the file on disk,
and **discards the per-blob key when it does** — correctly, since returning a ref
carrying a new key would hand back something that cannot decrypt the stored file.

Ingest then skipped the `blob` insert on that outcome. But the blob store writes
to the filesystem, which cannot join the SQL transaction, so an ingest that
failed *after* `put` left the file on disk with no row and no recoverable key.
Every later ingest of those exact bytes would get `AlreadyPresent`, skip the
insert again, and then fail inserting a `capture` referencing a `content_hash`
with no row — permanently, for that content. The original code called this
"harmless" in a comment. It is the opposite: it is a poisoned cache entry that
survives restarts.

`store_bytes` now believes a dedupe hit only when the row backing it exists;
otherwise it discards the orphan and stores the bytes again under a fresh key.
That recovery is safe *because* the store is content-addressed — the bytes are
identical either way, and only the unreadable copy is lost.

The test was A/B'd against a deliberately broken control: with the row check
short-circuited to `true`, it fails with

```
FOREIGN KEY constraint failed   (extended_code 787)
```

which is the real failure, not a proxy for it. The test also asserts up front
that a capture pointing at a non-existent blob is refused at all — if that
foreign key ever stops being enforced, the test would keep passing while proving
nothing.

## Security and privacy implications

- **Nothing here opens a socket.** `kokin-ingest` takes a `&dyn HttpCapability`
  and cannot construct one; the CI privacy lint (A-015) covers the crate
  automatically, since it greps all of `crates/`.
- **A replayed capture cannot claim to be live.** `from_fixture` is set by
  `ReplayHttp` on read and written straight to the row and the audit payload.
- **`capture_completeness` is recorded on every capture**, so a static-HTML fetch
  of a JavaScript-heavy page is never mistaken for what a user would have seen.
- **Media type is what the server said**, with parameters stripped and an
  unparseable or missing header becoming `application/octet-stream` rather than a
  guess. Claiming bytes are HTML when the server did not say so is exactly the
  unlabelled inference this project is meant to avoid.
- **Byte caps still apply** — ingest calls `BlobStore::put`, which enforces the
  limit during read (A-011).
- The audit payload carries the *canonical* locator, so tracking parameters do
  not leak into the log (A-013).

## Known limitations

1. **No file ingest yet.** The plan's increment 6 includes `file → blob →
   artifact`. Only the URL path is implemented; the file path needs a decision
   about how a local path becomes a `source`, and it belongs with the extractor
   that will consume it.
2. **Bodies are `String`, not bytes** — inherited from `HttpResponse` (5b
   limitation 4). Binary evidence cannot round-trip through ingest yet, so
   images and PDFs wait for the same change.
3. **`redirect_chain_json` is always `[]`.** There is no transport to produce
   redirects. The column is written honestly rather than omitted, but nothing
   exercises it, so A-004 stays `partial`.
4. **The `running` row is not reaped.** A process killed mid-fetch leaves a run
   that stays `running` forever. That is deliberate for now — it is evidence —
   but there is no UI or query that surfaces stale runs, and there should be
   before a user ever sees this.
5. **One transaction per ingest, no batching.** Fine for one URL at a time;
   a sweep over many targets will want a different shape.
6. **`transform_run` is written outside the ingest transaction** and is therefore
   not rolled back with it. That is the point — the failed run must survive — but
   it does mean a failure leaves a run row and no rows it refers to, which any
   future lineage query has to expect.
