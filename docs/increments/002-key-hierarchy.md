## Behaviour added

No user-visible behaviour; this is a library increment with no UI, as planned.

Three keys with different lifetimes: a passphrase-derived **KEK**, a random
**case master key** that actually encrypts case data, and a **recovery key**.
The CMK is stored only as ciphertext, wrapped independently under the KEK and
the recovery key.

This replaces increment 1's shortcut of feeding the passphrase straight into
SQLCipher's `PRAGMA key`. That was correct as a proof and wrong as a product:
it made the passphrase *be* the data key, so changing a passphrase would have
required re-encrypting the whole case, and a forgotten passphrase would have
been unrecoverable by construction.

The nine key tests, with the three that carry weight called out:

- round-trip recovers the master key
- wrong passphrase is rejected
- **a wrapped key cannot be transplanted into another case** — the reason AAD is
  a required parameter and not an optional extra
- tampering with the ciphertext is detected
- a recovery key unwraps the same master key
- **rotating the passphrase does not change the master key** — asserts the
  property the whole design exists for, and that the old passphrase stops
  working
- **`kdf_known_answer`** — see below
- profile ids round-trip, unknown ids rejected
- `Debug` never prints key material

detect being wrong from the start. So the expected value was cross-checked
against **`argon2-cffi` 25.1.0**, which binds the reference C implementation
(phc-winner-argon2), with identical inputs:

## Security and privacy implications

- Argon2id at 64 MiB / t=3 / p=1, above OWASP's 19 MiB floor. `p=1` because
  parallelism mainly helps an attacker with a GPU in this setting; memory
  hardness does the work.
- **KDF parameters live in the case header, not the binary.** Compiled-in
  parameters would make every existing case underivable the moment defaults were
  raised, with a symptom indistinguishable from a wrong passphrase.
- AEAD `aad` binds each wrap to its case id and KDF profile, so a wrapped key
  cannot be transplanted between cases or replayed under different parameters.
- `Secret` is zeroized on drop, `Debug` is redacted, and `to_hex` returns
  `Zeroizing<String>` so the hex form cannot leave a copy on the heap.
- `PartialEq` is constant-time via `subtle`, not derived. The derived version
  short-circuits on the first differing byte.
- `WrongKey` deliberately does not distinguish a bad passphrase from damaged
  ciphertext — an AEAD failure cannot tell them apart, and inventing the
  distinction would be a guess or an oracle.
- All five new dependencies are RustCrypto or ecosystem-standard, permissively
  licensed, and recorded in `docs/dependencies.csv` with purpose, licence,
  maintenance, size, security implications, and replacement strategy.

## The CI failure this increment also fixed

Run `31596323365` was the first time the Windows leg ran to completion, and it
**failed at `Build application bundle`**:

```
BEGIN failed--compilation aborted at /usr/share/perl5/core_perl/Params/Check.pm line 6.
Command failed: "perl" "./Configure" ... "VC-WIN64A"
```

`/usr/share/perl5/core_perl/` is msys2 perl. The step carried `shell: bash`,
which on a Windows runner is Git Bash and puts cygwin perl ahead of Strawberry
Perl on PATH; OpenSSL's `Configure` rejects cygwin perls for `VC-WIN64A`. The
`Test` step passed in the same run because it uses the default shell.

This is the failure mode already documented in ADR-0004 and written into the
comment above the perl-verification step — applied there, and then not applied
to the build step.

Fixed by invoking `node ui/node_modules/@tauri-apps/cli/tauri.js build --ci`
under the default shell. The `.bin/tauri` shim is a `/bin/sh` script, so using
it would drag bash back in; `tauri.js` is that shim's real target and `node`
runs it identically on both runners. **Verified locally with the exact CI
command**, producing the NSIS installer above. Confirmed the diagnosis directly:
in Git Bash on this machine, `which perl` is `/usr/bin/perl` — the msys perl.

## Known limitations

1. Nothing consumes `kokin-keys` yet. `kokin-store` still takes a passphrase
   directly; wiring the CMK into `PRAGMA key` is increment 3's job, along with
   the case header that stores the salt, profile id, and both wrapped keys.
2. No OS keyring integration. Planned behind a feature flag; deferred because it
   is platform-specific surface with no consumer yet.
3. The recovery key has no human-facing encoding. 32 raw bytes as hex is not
   transcribable; BIP39 or Crockford base32 is a UX decision belonging to the
   increment that builds case creation. Not a format decision — the key is 32
   bytes either way.
4. **No defence against memory disclosure while a case is open.** Zeroization
   bounds how long keys linger; a live process holding a decrypted CMK is
   inherent to letting the user read their own case. Threat model B1; adversary
   strength is D-008, still open.
5. No rekey (new CMK + re-encrypt) implementation — only rotation. Rekey needs
   the storage layer, so it belongs with increment 3.
