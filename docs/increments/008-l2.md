# Increment 8 — the analytical layer

Reference-workflow **step 5**. The layer the previous seven increments exist to
support: `kokin-ingest` recorded what was collected, `kokin-extract` recorded
what a parser read, and this records what a person concluded — under a rule that
makes the two impossible to confuse.

Migration 4 adds L2 (`entity`, `identifier`, `relationship`, `evidence_link`,
`assessment`) plus the registries they depend on (`entity_type`, `scale`,
`scale_value`). `kokin-graph` is the write path, and it loads the seven
confidence scales of ADR-0007 from `docs/data-model/scales/*.yaml`.

## The five ideas

**1. Nothing in L2 exists without an `evidence_link`, and the database is what
says so.** Every writer in `kokin-graph` takes the evidence in the same call and
writes the link *before* the row it grounds — because that is the only order the
schema accepts. `entity_requires_evidence` and its siblings refuse an entity,
identifier, or relationship whose `evidence_link` is not already there.

The check inside `kokin-graph` is a courtesy that produces a better error
message. The trigger is the guarantee, and
`the_rule_holds_even_going_around_this_crate` proves it by bypassing the crate
entirely and issuing the `INSERT` by hand. A rule enforced only by the code that
happens to call it is not enforced; the next caller writes its own statement and
the rule is gone.

This is the mechanism behind the acceptance criterion "graph edges open their
supporting evidence". It is not a screen someone remembered to build — it is the
only shape the schema permits.

**2. The rule holds backwards too.** Enforcing grounding only at insert would
leave it defeatable one statement later, so `evidence_link_keeps_l2_grounded`
refuses to delete the last link belonging to a row that still exists. To remove
an entity you delete the entity; you cannot quietly strip its basis and leave the
conclusion standing.

**3. A case carries what its words meant.** The scales are authored in
`docs/`, embedded at compile time, and **copied into the case**. `assessment`
has a composite foreign key into `scale_value(scale_id, scale_version,
value_key)`, so a value that is not in the scale it names cannot be written at
all.

The alternative — name the scale by id and keep the definitions in the binary —
is smaller and wrong. Revising a scale would silently restate every judgement
already made under it: an analyst who recorded "similar, unverified" under a
definition that required no corroboration would find it re-read under one that
does. `scale_is_immutable` refuses the in-place edit outright.

**4. `machine_assignable` is a control, not a comment.** Each scale value says
whether an automated pass may set it, and
`assessment_respects_machine_limits` enforces it on `INSERT` *and* `UPDATE` for
any actor prefixed `rule:` or `ai:` — the same prefixes ADR-0008 uses to keep
automated similarity from merging entities, so an actor string means one thing
across the whole case.

Concretely: until PoC P8 measures the username sweep's false-positive rate, a
rule may record that two identifiers *look* alike and may not record that they
belong to the same actor. That is A-019, new in this increment.

**5. There is no composite score, and the schema is tested for its absence.**
ADR-0007's argument is that *a column that exists will eventually be displayed*,
so `the_schema_has_no_composite_confidence_column` walks every column of every
table and fails on anything named like a total. `assessments_for` returns a list
and there is no `overall()` beside it.

## A bug the tests caught

`relationship-confidence.yaml` stated in its `threshold_rationale` that
*"nothing above `co_occurrence` is machine-assignable in Phase 1"*, and marked
**nothing** machine-assignable in its `values` block.

Each scale therefore states its machine ceiling twice: once in prose a human
reads, once in a field the database enforces. They disagreed, and the failure
mode was not the obvious one. It was not that a rule could assign too much — it
was that the extractor could not record the one thing it is entitled to observe,
`co_occurrence`, so the honest rating of a weak edge was unwritable and the
pressure would have been to leave such edges unrated altogether. An unrated edge
in a graph reads as a plain fact.

Nobody reading the file noticed. The first automated write did.
`the_machine_ceiling_matches_what_each_scale_says_in_prose` is now the cheap
version of that discovery, asserting each scale's documented ceiling against the
field.

The file was corrected in place rather than versioned to 2. The criterion is
narrow and worth stating so it does not erode: **a scale may be edited in place
only while no build containing it has been released**, since versioning exists to
protect assessments already made, and there are none. Once a version ships to a
user, `scale_is_immutable` and the README's rule apply without exception.

## The dependency decision

ADR-0007 mandates YAML; `serde_yaml` is deprecated and its successors are an
ambiguous field of forks. Measured rather than assumed (D-014):

| Candidate | Parser | Unsafe blocks | Transitive crates |
|---|---|---|---|
| `yaml_serde` (The YAML Organization) | `libyaml-rs` | ~240 | 5 |
| `serde_norway` | `unsafe-libyaml-norway` | ~248 | 5 |
| `serde-saphyr` | `granit-parser` | 1 | 9, one maintainer |

The unsafe count did not decide it, and that is the part worth being explicit
about: **this parser only ever sees bytes embedded at compile time from this
repository.** No user, case, or network input reaches it, so ~240 unsafe blocks
in a transpiled C parser are not adversary-reachable. What actually costs us is
the crate being abandoned a second time, so institutional provenance won.

The reasoning depends entirely on the input being trusted. If scales ever become
user-supplied — plugin manifests, imported case templates — this must be
revisited and `serde-saphyr` becomes the right answer. Both `dependencies.csv`
rows say so. The swap is one module.

## Security and privacy implications

- **A-006 (AI-asserted claim without evidence) moves to `partial`.** The general
  rule is now enforced by trigger for `entity`, `identifier`, and
  `relationship`. The `ai_suggestion` path — `cited_observation_ids_json`, and
  the human-only transition to `stance='asserted'` — is still planned, because
  that table does not exist yet.
- **A-019 (automated confidence inflation) is new and `partial`.** Covers
  `assessment`; the merge path is A-007 and stays planned until `er_*` lands.
- **Identifier normalisation is deliberately minimal.** Aggressive folding —
  stripping dots, unicode confusable mapping, plus-address removal — makes
  distinct identifiers collide, and a collision here does not present as a near
  miss. It presents as `same_identifier`, the strongest value the scale has. The
  original is always kept beside the normalised form so a bad fold stays
  visible. Email is the one case with structure worth respecting: the domain is
  case-insensitive by specification and the local part is not, so only the domain
  is lowercased.
- **`evidence_link` may point only at L0 and L1 rows.** An analytical row is
  never evidence for another analytical row, because that is how a conclusion
  comes to support itself.
- **No new egress.** `kokin-graph` opens no sockets; the CI grep covers
  `crates/` by directory and needed no change.

## Known limitations

1. **`claim` and `ai_suggestion` are not built.** ADR-0006 lists both in L2.
   Adding them means a migration and their own grounding triggers — which the
   design anticipates: `evidence_link.subject_kind` is deliberately *not*
   constrained to a list, so a new L2 table adds a trigger rather than forcing a
   rebuild of `evidence_link`.
2. **A typo'd `subject_kind` creates an orphan link.** The cost of that
   flexibility. Such a link satisfies no trigger and grounds nothing, so it is
   inert rather than dangerous, but nothing detects it.
3. **The `er_*` tables of ADR-0008 are absent.** Merge, split, undo, and
   alternate hypotheses are a later increment; A-007 stays `planned`.
4. **Reassessment keeps one row and puts the history in the audit chain.** That
   is a real trade: the chain records that a value changed, but a UI wanting
   "show me this dimension's history" must read the chain rather than the table.
5. **No reader for supersession, and no `needs_review` flag.** ADR-0006 requires
   a claim resting on a superseded observation to be flagged with a diff.
   Increment 7 left this open and increment 8 does not close it — `needs_review`
   exists as a `review_status` value, but nothing sets it automatically.
6. **`assess` uses the highest scale version in the case.** Correct today,
   because no scale has a second version. When one does, "assess under the
   version this case already used" and "assess under the newest available" stop
   being the same thing, and the choice must become explicit.
7. **`entity_type.form_json` is unused.** The column exists so adding per-type
   forms is not a migration; nothing reads it yet.
8. **The entity registry is 12 types, not ~25.** These are the types Phase 1's
   pipeline actually produces or refers to. A registry padded with types nothing
   can create is a menu of dead ends; adding the rest is an `INSERT`.
9. **Nothing creates entities automatically yet.** Extraction produces
   observations; promoting them to entities is a human act through this API.
   That is deliberate for now, but it means the co-occurrence path is exercised
   by tests rather than by the product.

## Manual verification

**Control 1 — remove `machine_assignable: true` from `co_occurrence`.** Fails
exactly `the_machine_ceiling_matches_what_each_scale_says_in_prose` and
`two_things_on_one_page_are_related_at_co_occurrence_and_no_higher`, and nothing
else. Restored, all pass.

**Control 2 — drop the `entity_requires_evidence` trigger. This one found a
broken test.**

`the_rule_holds_even_going_around_this_crate` **passed with the trigger gone**.
It was never testing the trigger: `entity_type` is empty until `initialise()`
runs, and the test issued its raw `INSERT` before that, so the row was refused by
the `type_key` foreign key. The right outcome for the wrong reason — a test that
reported a guarantee nobody was providing, and which would have gone on reporting
it after the trigger was deleted.

Fixed by seeding the registries first, asserting the type really is present so
the setup cannot silently rot again, and then showing that the *same* insert
succeeds once its `evidence_link` exists — which pins the refusal to the missing
evidence rather than to anything else. Re-run with the trigger still dropped: the
test now fails. Trigger restored: 21 pass.

The lesson generalises, and it is the reason this project runs A/B controls at
all rather than trusting green. **A passing test proves something failed, not
that the thing you meant failed.** The store-level twin,
`nothing_in_l2_can_be_created_without_evidence`, failed correctly throughout,
which is why having the rule tested at two levels was worth the duplication.
